# DESIGN-note：视频号流式端点改为「分窗全读」，CDN 连接不再受下游速率牵制

对应 issue：#16。上一批方案见 `docs/sessions/sph-download/design.md`，本文只覆盖本批改动。

## 目标

任何速度的客户端（含中途停顿一两分钟的）通过 `GET /api/stream/wechat_channels/{sph_code}`
都能拿到完整、可校验的解密 mp4；长视频不再在十几 MB 处断流。

## 非目标

- 不做落盘缓存、不做跨请求复用（没有第二个消费者，先不引入磁盘状态）。
- 不改解密算法、不改鉴权、不改 429 并发闸、不改 sph 短码校验。
- 不改 `POST /api/resolve` 的任何行为。
- 不要求下游改造；下游自己按 Range 续传属纵深防御，另开 issue。

## 实测机理（2026-09-02，本机与 fordeal 生产容器各跑一遍）

issue #16 写的「微信 CDN 单连接约 16MB 隐性限额」**不成立**，按下述真实链路实现：

| 场景 | 结果 |
|---|---|
| 本机 / 生产容器内直连 CDN，不带 Range 一次拉完 415MB | 200 完整，约 71 s，5.8 MiB/s，未断 |
| 生产容器内 `Range: bytes=100000000-` 拉到尾 | 206 完整，未断 |
| 读 1 MiB 后停 90 s 不读，再继续 | 收到 16.4 MiB 后 CDN 关连接 |
| 以 200 KB/s 慢速读 | 约 77 s、11.7 MiB 后 CDN 关连接 |

生产日志里 6 次失败每次持续 80 到 90 s，吐给下游约 200 KB/s。机理：现有实现是纯透传，
CDN 到本服务的读取速率等于本服务到客户端的写出速率；客户端慢或停顿时，CDN 在约 60 s
推不动数据后主动关闭连接。所谓 16 MB 只是断开前两端 socket 缓冲能囤下的量
（两台机器 `net.ipv4.tcp_rmem` 上限均为 6 MB，加上对端发送缓冲），与文件大小和 CDN 配额无关。

另两个影响设计的实测事实：

- TikHub 每次返回的 `(full_url, decode_key)` 都不同；两对 URL 的前 131072 字节密文不同，
  之后的字节逐字节相同。
- TikHub 的 `file_size` 不可信（报 2450521066，CDN 实际 435768323），继续以 CDN 为准。

## 方案要点与已否决方案

- **要点 1：唯一不变式是「不能有任何 CDN 响应处于读了一半、正在等客户端的状态」。**
  所有 CDN 请求都是有界 Range 窗口（默认 4 MiB，`STREAM_WINDOW_BYTES`），每个窗口一次性
  读完进内存后才向客户端吐字节。CDN 每个请求 1 s 内结束，从此感知不到客户端快慢。
- **要点 2：续传是分窗的自然产物，不是独立机制。** 窗口读失败时它的字节还没向客户端吐过，
  重取同一窗口即可，没有半截状态。单窗口最多 3 次，单次请求总重试预算 20 次；超预算时
  响应头未发出返回 502，已发出则断连接（客户端收到长度不足，这与现状一致，是 HTTP 的物理上限）。
- **要点 3：首个窗口即长度探针。** 第一个 206 的 `Content-Range` 完整长度给出总长，响应头
  在此之后才发，`Content-Length` 始终准确。后缀 Range（`bytes=-N`）先请求 `bytes=0-0`
  取总长再换算成绝对偏移。
- **要点 4：CDN 对有界窗口必须回 206。** 唯一例外：窗口起点为 0 且 CDN 回 200 且
  `Content-Length` ≤ 窗口大小（整个文件比一个窗口还小），此时把 200 当作整文件读完。
  其余 200 一律按「CDN 忽略 Range」失败，不做「从全量流丢弃前 N 字节」类补偿。
- **要点 5：URL 过期换对。** 某窗口收到 401/403/404/410 时向 TikHub 重取一对
  `(full_url, decode_key)`，每个请求最多换 1 次；仅允许用于起点 ≥ 131072 的窗口（之后的
  字节与密钥无关），起点更小的窗口换对直接失败——实际上前 128 KB 总在第一个窗口内、
  1 s 内取完，这条只是封死错误路径。
- **要点 6：预读一个窗口。** 消费当前窗口时后台取下一个，客户端快时不被 CDN 往返拖慢。
  单流内存上限为 2 个窗口，默认 8 MiB；乘 `MAX_CONCURRENT_STREAMS`（默认 4）为 32 MiB。
  客户端取消或断开时预读任务必须被取消并关闭其 CDN 响应。
- **要点 7：解密不变。** `xor_chunk(raw, key, offset)` 按绝对偏移计算，窗口边界与
  131072 密钥流边界互不对齐也不影响正确性，由测试锁死。
- **已否决：断线后 `Range: bytes=<offset>-` 重连（issue #16 原提案）。**
  每个新连接照样在约 60 s 后被掐，415 MB 以 200 KB/s 下载要重连二十多次，且会把
  「CDN 有 16 MB 限额」这个错误认知固化进代码与文档。
- **已否决：先整文件落盘再服务。** 能顺带缓存重复下载，但引入磁盘、清理、同文件并发等
  状态，当前没有第二个消费者。
- **已否决：调大内核接收缓冲。** 只是把阈值从 16 MB 挪到几十 MB，机理未变。

## 关键不变式

每条写明「代码在哪、哪个测试锁死」，实现卡以此为验收清单。

1. **CDN 响应在向客户端 yield 前已被完整读完**：窗口读取器在 `app/api/stream.py`；
   测试里的假 CDN 记录每个响应「是否在下一次客户端 yield 之前被读完」，断言全部为真。
   红验：把「读完再吐」改成边读边吐，该断言必须变红。
2. **字节正确性**：任意窗口大小（含不整除 131072、比 131072 小、比文件大）下，
   拼接结果与「整文件解密后切片」逐字节相同；沿用现有 Range 矩阵测试，参数化窗口大小。
3. **响应头正确性**：`Content-Length` / `Content-Range` / 状态码由首窗口的 206 元数据推导，
   200（无 Range）与 206（有 Range）两种形态，以及后缀 Range，各有测试。
4. **窗口失败重试**：第 N 个窗口短包或传输错误 → 同窗口重取成功 → 客户端拿到完整文件；
   连续失败超过 3 次 → 断连接；重试预算耗尽前响应头未发出 → 502。
5. **换对规则**：窗口 403 且起点 ≥ 131072 → 重取 media 后成功；起点 < 131072 → 失败；
   每个请求换对最多 1 次。
6. **取消清理**：客户端断开时当前与预读的 CDN 响应都被 `aclose`，沿用
   `test_client_disconnect_acloses_upstream` 并扩展到预读窗口。
7. **416 语义不变**：起点 ≥ 总长时透传 CDN 的 416 及 `Content-Range: bytes */L`。

## 验收路径

单测绿不算数：本缺陷在本机复现不出来，必须在真实入口跑。

1. 入口：fordeal 上部署的服务（或本机起 uvicorn 后用同一脚本）。
2. 步骤：
   - `POST /api/resolve` 取 `https://weixin.qq.com/sph/AHaM8SrlXX`（415 MB）的 `video_url`；
   - 客户端 A：正常速度拉完整文件，计算 md5；
   - 客户端 B：读 1 MiB 后停 90 s，再继续拉完，计算 md5；
   - 客户端 C：全程限速 200 KB/s 拉前 64 MiB（`Range: bytes=0-67108863`），计算 md5；
   - 对照：直连 CDN 拉同一 URL 全文件，本地用 `generate_keystream` 解密后计算 md5 与切片 md5。
3. 预期：A、B 的 md5 与对照相同且 `Content-Length` 等于 CDN 实际大小；C 的 md5 与对照切片相同，
   状态码 206；服务日志无 `upstream failed`。
