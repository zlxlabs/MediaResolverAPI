# DESIGN-note：微信视频号接入 —— 元数据解析 + 服务端流式解密代理

## 目标

让 `POST /api/resolve` 接受微信视频号分享链接（`https://weixin.qq.com/sph/…`），像其他 8 个
平台一样返回元数据与一条 `video_url`；**客户端按这条 `video_url` 下载到的必须是可直接播放的
标准 mp4**，不需要客户端自己做任何解密。

## 非目标

- **不做 mp3 / 音频提取**（本轮已明确排除；将来要做是独立能力，涉及 ffmpeg 与任务队列）。
- 不做视频号的用户主页、合集、评论、直播、公众号文章等其他 TikHub 视频号接口。
- 不做浏览器 `<video>` 标签的免鉴权直链播放（stream 端点沿用 `X-API-Key` 请求头鉴权，
  与现有接口一致）。
- 不改现有 8 个平台的任何行为。

## 方案要点与已否决方案

### 背景事实（均已实测确认，非推断）

1. TikHub 端点 `POST /api/v1/wechat_channels/v2/fetch_video_detail`，传 `share_url` +
   `raw=false` 即可，实测 HTTP 200。返回 `data.id`（object_id）、标题、作者、点赞/收藏/转发/
   评论、时长、宽高、封面、`media.full_url`（已拼好防盗链 token 的 CDN 直链）、
   `media.decode_key`。**没有播放量**（`read_count` 恒为 0）。
2. **视频文件前 131072 字节被 XOR 加密**，其余为明文。还原需要用 `decode_key` 生成 128KB
   密钥流。这是视频号与其他所有平台的**唯一本质差异**。
3. **每次调 detail 接口都会返回新的 CDN 链接和新的 decode_key**，两者必须成对使用，跨批
   混用必然解密失败。
4. 视频 CDN **支持 HTTP Range 请求**（实测 206），因此流式代理可以做，内存占用恒定。
5. TikHub **没有**提供解密后的文件或解密端点（24 个微信相关端点已逐一确认）。

### 要点

- **要点 1：`video_url` 指向本服务，且是稳定 URL。**
  resolve 返回 `video_url = {BASE_URL}/api/stream/wechat/{object_id}`。这条 URL 不含任何
  会过期的 token，因此**现有的 `video_cache` 缓存机制完全不用改**——缓存它是安全的。
  链接会过期这件事被整个推到 stream 端点内部解决。

- **要点 2：stream 端点无状态，每次请求现调 TikHub 取配套的 (CDN 链接, decode_key)。**
  客户端 `GET /api/stream/wechat/{object_id}` 时，服务端才去调一次 detail 拿到当次配套的
  链接与密钥，随即流式拉取 CDN、边拉边解、边回传给客户端。
  代价是每次下载多一次 TikHub 计费调用；换来的是**永远不会出现"链接过期"这个失败模式**，
  也不需要在服务端维护 (url, key) 的短期状态账本。

- **要点 3：解密只碰前 128KB，之后字节直通。**
  流式管道里维护一个"已转发字节数"游标：游标 < 131072 的部分与密钥流逐字节异或，
  越过 131072 之后原样透传。密钥流是 decode_key 的纯函数、可按 key 缓存（已由公开实现的
  代码注释确认）。

- **要点 4：Range 请求透传给 CDN，偏移量参与解密计算。**
  客户端带 `Range: bytes=N-` 时，把 Range 原样转发给 CDN，并用 N 作为解密游标的起点：
  N ≥ 131072 则全程直通，N < 131072 则从密钥流的第 N 字节开始异或。
  这是本方案最容易写错的地方，会用专门的测试轴覆盖（见「关键不变式」）。

- **要点 5：URL 识别必须按路径判，不能只按域名。**
  现有 `url_parser.PLATFORM_DOMAINS` 是纯「域名 → 平台」映射，而 `weixin.qq.com` 这个域名
  同时承载公众号（`mp.weixin.qq.com`）等其他业务。视频号必须靠路径前缀 `/sph/` 区分。
  这是本次接入对 url_parser 的唯一结构性扩展。

- **要点 6：video_id 走已有的 by_url 兜底路径。**
  分享短链里的 `AOzokRxWHz` 不是 object_id，在 URL 解析阶段拿不到真实 id。把 `wechat` 加进
  已有的 `URL_FALLBACK_PLATFORMS`，用原始 url 调 TikHub，解析成功后由 `resolve.py` 现成的
  回填逻辑写回真实 object_id。**这条路径快手和 Instagram 已经在用，不是新机制。**

### 已否决

- **否决：只返回加密直链 + decode_key，让客户端自己解密。**
  改动最小，但把一个非平凡的密码学还原过程推给每一个调用方，等于这个服务对视频号只完成了
  一半的工作。（本轮已明确选择服务端代理。）
- **否决：resolve 时就把 (CDN 链接, decode_key) 存进服务端状态，stream 时取出来用。**
  省一次 TikHub 调用，但引入了一份带过期语义的状态账本，且 CDN 链接的实际有效期未知——
  一旦过期就是一个只在"解析后隔了一会儿才下载"时才复现的间歇性故障。用要点 2 的无状态
  方案把这个失败模式整个消掉，值这一次 API 调用。
- **否决：用 Python 的 wasm 运行时直接调微信官方的解密 wasm。**
  已核实该 wasm（3.6MB）走 embind + asyncify，导出表里只有 `malloc/free/dynCall_*/asyncify_*`，
  解密函数经 embind 注册，需要实现 53 个宿主导入才能起跑。不现实。
- **保留的备选（方案 B）：Node + 无头浏览器侧车服务生成密钥流。**
  社区现成方案就是这么做的。仅在纯 Python 实验卡失败时启用；启用则本方案多一个常驻依赖，
  部署复杂度显著上升。**当前实验卡正在跑，结论未定。**

## 关键不变式

1. **配套性**：用于解密的 `decode_key` 与被解密的字节流，必须来自同一次 TikHub detail 响应。
   代码上体现为二者在同一个函数作用域内取得、不经任何缓存中转。
   （锁死于：stream 端点的单元测试，断言每次请求都发起了新的 detail 调用。）
2. **解密边界**：当且仅当文件绝对偏移量 < 131072 的字节被异或；偏移量 ≥ 131072 的字节必须
   与 CDN 原始字节逐字节相同。
   （锁死于：Range 测试轴 —— `0-`、`0-131071`、`0-131072`、`131071-131073`、`131072-`、
   `200000-`、无 Range 共 7 格，每格断言输出与"整体下载后再截取"一致。）
3. **稳定 URL**：`resolve` 返回的 `video_url` 不含任何带时效的 token，同一 object_id 两次
   解析得到完全相同的字符串。（锁死于：resolve 层测试断言 video_url 全等。）
4. **内存恒定**：流式转发过程中不得把整个文件读进内存或落盘。实测样本是 2.45GB 的两小时
   视频，任何一次性读取都会打爆服务。（锁死于：stream 实现里禁止出现 `.read()` 全量读，
   审查时按此项逐行核对。）
5. **密钥流纯函数性**：`generate_keystream(k)` 对同一 k 恒定返回同一 128KB 字节串。
   （锁死于：实验卡的 `constraint_A` 判据 —— 两组不同 key 的真实样本满足 K1^K2 == E1^E2 的
   全部 131072 字节。）
6. **不污染其他平台**：本次改动后，现有 8 个平台的解析行为与响应字段零变化。
   （锁死于：现有测试全量绿。）
7. **上游断流即失败**：CDN 连接中断时，本次响应立即失败并留 `ERROR` 日志，不重取链接、不
   拼接响应。断点续传由客户端带 `Range` 重发请求完成，服务端不维护跨请求续传状态。
   （锁死于：`test_upstream_disconnect_terminates_response_with_error`。）
8. **客户端断开必须关闭上游**：客户端提前断开时，服务端与 CDN 之间的流必须随之关闭，
   不得留下悬挂连接继续消耗带宽。
   （锁死于：模拟客户端断开的测试，断言上游 response 的 `aclose` 被调用。）
9. **并发下载有上限**：同时进行的流式下载数受一个可配置上限约束，超限请求返回 429，
   而不是全部一起变慢直至超时。
   （锁死于：并发超限测试断言第 N+1 个请求拿到 429。）

## 网络异常与失败模式（本方案的主要新增风险面）

从「返回第三方直链」变成「自己当中转」，失败面从客户端搬到了服务端。逐类列明与处置：

| 异常 | 发生时机 | 影响 | 处置 |
|---|---|---|---|
| 上游 CDN 中途断流 | 响应头已发出、字节已在传 | **无法再改 HTTP 状态码**，客户端只会收到字节数不足的残缺响应 | 本次响应直接终止并留 `ERROR` 日志；客户端带 `Range` 重发 |
| 客户端取消下载 | 传输中 | 上游连接悬挂，白耗带宽与连接数 | 不变式 8 |
| TikHub 失败 / 限流 | 响应头**尚未**发出 | 可干净返回 502 | 强制「先同步取到 (链接, 密钥) 成功后才开始 StreamingResponse」 |
| 本机带宽 / 连接数打满 | 高并发或大文件 | 单个 2.45GB 下载即可占满小机器上行，多个并发全部卡死 | 不变式 9 的信号量上限 |
| 反代 / LB 超时掐断长连接 | 慢网络下的长时间传输 | 表现同「上游断流」但发生在下游 | 部署侧配置，上线前确认 nginx / 云 LB 的超时与缓冲设置 |

**续传为什么是安全的（已实测，非推断）**：同一视频连续两次请求 detail，拿到两把不同的
`decode_key`，但 `md5` 字段恒为 `6b572a0162a65730c41bb58dbafa2453`，且偏移 200000–300000
这段明文区的 100001 字节**逐字节完全相同**。故文件内容跨请求恒定，换一条新链接即可按绝对
偏移续上。额外性质：**续传点 ≥ 131072 时，续传段全是明文，新 key 不参与运算**，续传逻辑
退化为纯透传。

## 验收路径

1. **入口**：真实的 `POST /api/resolve`，跑在本地 `uvicorn` 起的服务上（不是库函数调用，
   不是单测）。
2. **步骤**：
   1. `POST /api/resolve` 带 `{"url": "https://weixin.qq.com/sph/AOzokRxWHz"}` 与
      `X-API-Key`，检查返回的元数据字段与 `video_url`。
   2. 用返回的 `video_url` 发一次带 `Range: bytes=0-131071` 的 GET，把前 128KB 存盘，
      校验偏移 4..8 处是 `ftyp`。
   3. 再发一次不带 Range 的 GET，用 `curl` 只取前 2MB 后中断，用 `ffprobe` 确认该片段能被
      识别为合法 mp4（有 moov/时长信息）。
   4. `GET /api/platforms` 确认 `wechat` 出现在列表里。
   5. 现有测试套件全量跑一遍，确认零回归。
3. **预期**：第 1 步返回 `success: true` 且作者为「晓辉博士」、标题为「对谈张笑宇：AI重塑
   组织与生活方式」；第 2 步 `ftyp` 校验通过；第 3 步 `ffprobe` 能读出视频流信息；
   第 4 步列表含 `wechat`；第 5 步全绿。

## 需要留意的风险（不阻塞开工，但要知道）

- **带宽与超时**：服务器成了视频流量的中转站。两小时长视频 2.45GB，反向代理与 uvicorn 的
  超时配置可能需要调整。上线前需确认部署环境（nginx / 云厂商 LB）对长连接大响应的限制。
- **风险等级**：用户已确认本仓为 `internal`（review 轮次上限 5）。仓库里尚无 `risk-tier:`
  单行声明，卡 4 顺手补上。
  **卡 3 例外**：其改动核心是失败路径与资源账本（断流续传、连接清理、并发信号量），
  按 infra/状态机类 diff 规则，收敛条件升一档执行 —— 连续 2 轮无新增 P1 才算收敛。
- **播放量字段**：视频号的 `view_count` 恒为 0，会以 `null` 返回，README 需注明。
10. **字节偏移对账**：任何一次从上游取得的字节流，其实际起始偏移必须经 `Content-Range` 与本地记账偏移对账一致后才可被消费；无法对账即视为该次上游失败。
   （锁死于：`test_range_matches_full_download_slice`、`test_initial_range_mismatch_fails_before_streaming`、`test_initial_range_missing_content_range_fails_before_streaming`、`test_initial_range_malformed_content_range_fails_before_streaming`、`test_no_range_206_start_zero_reconciles_before_streaming`、`test_no_range_206_nonzero_start_fails_before_streaming`。）
